    other -> flat optimum; results do not depend on exact hyperparameters.
  - Tuning gain was small compared with the untuned models of Step 4:
    LR 0.437 -> 0.438, RF 0.465 -> 0.470. Performance looks limited by the
    information in the pre-call features (~0.47 PR-AUC), not by tuning.

  FINDINGS
  - All models are far above the floor: PR-AUC ~0.44-0.47 vs 0.113 random.
  - Random Forest and XGBoost beat the baseline in EVERY fold; the gain
    (+0.03) is ~4x larger than its fold-to-fold variation -> a real, consistent
    improvement.
  - Decision Tree is NOT reliably better than the baseline (+0.006, only 3/5
    folds, smaller than the variation).
  - RF vs XGBoost: difference 0.003 PR-AUC, far below the fold std (~0.017)
    -> statistically a tie.
  - At threshold 0.5: RF is more precise (0.411) and XGBoost finds more
    subscribers (recall 0.631). This is a threshold choice, tuned in Step 6.
  - Business metric: calling the top-scored 20% of clients finds ~64% of all
    subscribers with RF/XGBoost (62% LR), i.e. 3.2x random calling.
  - Accuracy again misleads: "always no" (0.887) beats every real model on
    accuracy while finding nobody.

  - The CV score (not the train score) is what we compare, so the gap does
    not invalidate RF, but it is a point in XGBoost's favour.

     0.625->0.578, 0.643->0.630, 0.642->0.626)
  - SMOTE never improved ranking quality and hurt all tree models, while
    taking 2-5x longer. Likely cause: SMOTE interpolates one-hot columns,
    creating unrealistic "half-category" clients.
  - SMOTE shifts predictions towards higher precision / lower recall at 0.5
    (e.g. XGBoost recall 0.631 -> 0.389), the opposite of what it is meant to do.
  -> DECISION: class weights confirmed as the imbalance strategy.

7. TECHNICAL NOTE - PARALLELISM
-------------------------------------------------------------------------------
  Process-based parallel search (GridSearchCV(n_jobs=-1)) crashes with the
  installed joblib 1.5.1 on Windows / Python 3.13 ("No module named
  '_posixsubprocess'"). Searches therefore run folds sequentially, while RF
  and XGBoost use all CPU cores internally (thread-based n_jobs=-1).
  Results are unaffected; only runtime is longer.
