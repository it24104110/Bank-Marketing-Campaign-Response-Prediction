-------------------------------------------------------------------------------
0. THE KEY PRINCIPLE: TWO KINDS OF PREPROCESSING
-------------------------------------------------------------------------------
  Row-level cleaning   = fixed rules, learns nothing from the data
                         -> safe to apply before the train/test split
                         -> function clean_rows()
  Fitted transformations = one-hot encoding, scaling, imbalance handling
                         -> learn from the data, so they are fitted on TRAINING
                            data only, inside a scikit-learn Pipeline together
                            with the model (re-fitted on every CV fold)
                         -> function build_preprocessor("linear" / "tree")
  This prevents information from the test set leaking into training.


-------------------------------------------------------------------------------
1. ROW-LEVEL CLEANING
-------------------------------------------------------------------------------
1.1 Remove exact duplicates                                         [D8]
    WHAT:   dropped 12 exact duplicate rows.
    WHY:    the same row could otherwise appear in both train and test.
    RESULT: 41,188 -> 41,176 rows; yes-rate 11.2654% -> 11.2663% (unchanged).

1.2 Drop duration                                                   [D3]
    WHAT:   removed the call-duration column.
    WHY:    only known AFTER the call (EDA: AUC 0.818, strongest feature) ->
            would inflate results and cannot be used for pre-call ranking.
    RESULT: 20 columns remain. A with/without benchmark will be shown in
            modelling, on training data only.

1.3 pdays -> contacted_before flag                                  [D10]
    WHAT:   new feature contacted_before = 1 if previous > 0, else 0;
            raw pdays dropped.
    WHY:    pdays = 999 is a placeholder in 96% of rows, and 4,110 rows
            contradicted its documented meaning.
    RESULT: the flag lines up EXACTLY with poutcome:
              contacted_before = 0  <->  poutcome = nonexistent (35,551)
              contacted_before = 1  <->  poutcome = failure (4,252) / success (1,373)
            -> confirms the flag is consistent.
            Yes-rate: never contacted 8.83%  vs  contacted before 26.65%.

1.4 default -> "no" vs "not_no"                                     [D13]
    WHAT:   merged the 3 "yes" rows with "unknown".
    WHY:    3 rows are too few to learn from; both mean the bank cannot
            confirm the client is free of default.
    RESULT: no = 32,577 | not_no = 8,599.

1.5 education: "illiterate" -> "basic.4y"                           [D14]
    WHAT:   merged 18 "illiterate" rows into the closest level.
    WHY:    too rare to learn from.
    ALSO:   education is ONE-HOT encoded, not ordinal - EDA showed the
            yes-rate is not ordered by level, and "unknown" has no order.
    RESULT: 7 levels remain (university.degree 12,164 ... unknown 1,730).

1.6 Cap campaign at 10                                              [D9]
    WHAT:   values above 10 set to 10.
    WHY:    values up to 56 are real but sparse; capping keeps the meaning
            ("called 10+ times") but stops extreme values from dominating
            the scaled Logistic Regression input. Trees are unaffected.
    RESULT: 869 rows (2.11%) capped; their yes-rate is only 3.11%.
    NOTE:   campaign is kept although it is only "partly" known before
            contact: the model is re-scored before each call attempt, and
            the number of attempts so far is known at that moment.

1.7 Target encoding
    WHAT:   y: yes -> 1, no -> 0.

1.8 Verification
    The step-by-step result is IDENTICAL to clean_rows(raw)
    (pd.testing.assert_frame_equal passed).
    Saved: data/processed/bank_clean.csv  (41,176 rows x 20 columns)

    NO rows were removed as outliers, and "unknown" values were kept as
    their own category (decisions D7, D9).

3. FEATURE SELECTION (training data only)                           [D15]
-------------------------------------------------------------------------------
3.1 Statistical association with the target (train set)
              feature       p-value   Cramer's V
              housing        0.2599      0.009     not significant
              loan           0.9218      0.002     not significant
              day_of_week    0.0307      0.018     significant but weak
              poutcome       0.0000      0.325     (for comparison)

3.2 Effect on 5-fold cross-validated performance (quick, UNTUNED models)
    model         feature set                          PR-AUC (std)      ROC-AUC (std)
    LogReg        all features                         0.4365 (0.0126)   0.7876 (0.0072)
    LogReg        drop housing + loan                  0.4368 (0.0131)   0.7878 (0.0071)
    LogReg        drop housing + loan + day_of_week    0.4351 (0.0127)   0.7881 (0.0081)
    RandomForest  all features                         0.4641 (0.0159)   0.7941 (0.0073)
    RandomForest  drop housing + loan                  0.4646 (0.0180)   0.7958 (0.0093)
    RandomForest  drop housing + loan + day_of_week    0.4593 (0.0159)   0.7935 (0.0078)

3.3 Decision
    - DROP housing and loan: no significant association, and removing them
      changes PR-AUC by only +0.0003 (LR) / +0.0005 (RF) - far smaller than
      the fold-to-fold std (~0.013-0.018). Simpler model, no loss.
    - KEEP day_of_week: weak but significant (p = 0.03), and removing it
      lowered PR-AUC in BOTH models (-0.0017 LR, -0.0048 RF).

3.4 Early signal (not a final result)
    Even untuned models reach PR-AUC ~0.44-0.46, about 4x the 0.113 of
    random guessing, and ROC-AUC ~0.79. The features carry real signal.
    Random Forest is slightly ahead of Logistic Regression already.
